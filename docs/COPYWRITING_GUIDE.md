# Dust and Ash 文案规范

## 1. 目的

本规范用于统一 Dust and Ash 的物品描述、进度描述、指南书正文与模组简介。

文案借鉴《艾尔登法环》物品说明的组织方式：先确认物件，再陈述效用，以有限的来历补充意义，最后在事实允许时留下余韵。项目不模仿原作专有名词、角色、历史或具体句子。

## 2. 已确认的创作口径

- 中文采用自然、克制的现代书面语，不刻意制造翻译腔。
- 只使用代码、配置、配方、模型、资源和用户明确确认的设定。
- 不自行创造人物、组织、年代、战争、宗教或关键历史事件。
- 特殊武器与饰品使用完整描述；普通工具、材料和基础装备保持简短。
- 详细描述原则上按“物件 → 效用 → 条件或代价 → 来历 → 余韵”组织。
- 某一环节没有已确认事实时直接省略，不以模糊传闻填空。

## 3. 参考文本提炼

研究样本覆盖武器、护符、消耗品、材料、护甲、法术与关键道具。主要参考：

- [Elden Ring Wiki.gg](https://eldenring.wiki.gg/wiki/Elden_Ring_Wiki)
- [BWIKI 艾尔登法环](https://wiki.biligame.com/eldenring/首页)

从样本中提炼出的稳定结构如下：

1. **物件定义**：材质、形态、所属者或制作方式。
2. **明确效用**：直接说明能做什么，不以气氛替代规则。
3. **局部来历**：只给出与物件直接相关的事件或用途。
4. **余韵收束**：通过因果、反差、推论或疑问拓展意义。

低阶材料通常只需要前两项。承担核心机制或世界信息的物件才使用完整结构。

## 4. 文本层级

### 4.1 默认 Tooltip

- 只显示一条简化描述。
- 说明物件身份与核心能力。
- 不显示精确数值。
- 推荐 16～30 个汉字，最多承载两个信息点。

### 4.2 按住 Alt

- 详细描述完全替换简化描述，两者不同时出现。
- 特殊装备使用 3～5 行；普通工具使用 1～2 行。
- 每行只承担一个信息单位。
- 顺序优先采用：物件、效用、条件或代价、来历、余韵。

### 4.3 按住 Shift

- 不新增独立数值列表。
- 精确数值直接插入当前显示的简述或详细描述。
- 插入数值不得改变句子的含义和信息顺序。
- 数值使用黄色；正文沿用白色或灰色。

### 4.4 同时按住 Alt 与 Shift

- 显示带精确数值的完整详细描述。
- 不增加额外标题、表格或重复句。

## 5. 品类模板

### 5.1 特殊武器

1. 说明形制、基底材料或结晶来源。
2. 说明核心攻击机制。
3. 说明主动能力、触发条件与代价。
4. 在有事实依据时，以结晶性质或制作结果收束。

### 5.2 饰品

1. 说明饰品形态、槽位及所用结晶。
2. 说明常驻能力。
3. 说明条件触发、目标选择与伤害或回复。
4. 说明冷却、例外和代价。
5. 在有事实依据时，以可观察现象收束。

### 5.3 普通工具

1. 说明用途。
2. 说明必要资源、成功条件、消耗或限制。

不为普通工具强行补写制造者或历史。

### 5.4 材料与结晶

1. 说明可观察形态或性质。
2. 说明已确认用途或来源。

若没有独特机制，一至两句即可。

### 5.5 关键道具

1. 说明物件本身。
2. 说明它与某个已确认过程的关系。
3. 说明它造成或预示的规则变化。

### 5.6 指南书

- 指南书负责解释操作顺序，不承担未经确认的世界历史。
- 优先写玩家可执行的步骤，再解释机器或材料的作用。
- 链接、配方页和多方块结构页保持 Patchouli 标记完整。
- 不直接暴露 Java 字段名、NBT、事件名或内部注册实现。
- 数据标签只有在玩家确实需要配置或扩展时才显示资源位置。

### 5.7 进度描述

- 描述玩家刚刚完成的事实及其直接意义。
- 一般使用一句话，建议 12～28 个汉字。
- 不写与触发条件无关的笑话、括号吐槽或未确认设定。
- 标题可以保留象征性；描述必须清楚。

## 6. 语言规则

- 以物件为主语，优先使用“持有者”“佩戴者”“目标”，少用“玩家”或第二人称。
- 使用陈述句。问句只用于已有事实确实留下的悬念。
- 每件物品最多使用一次“据说、似乎、或许”等不确定标记。
- 少用空泛评价，如“强大、神秘、终极、史诗、恐怖”。
- 诡异感来自具体事实，不来自连续堆叠形容词。
- 中文使用全角标点；省略号使用“……”；不混用中英文标点。
- 语言文件正文不嵌入 `§` 颜色码，颜色由渲染代码统一控制。
- 英文不逐字回译中文，应保持同一事实、段落功能与克制语气。

## 7. 机制与数值

- 精确区分“免疫伤害、减少伤害、回复生命、清除受击无敌时间”。
- 玩家可见单位统一为“秒、格、层、级、%”。
- 不在文案中使用 tick、Tag、NBT、事件、倍率字段名等实现术语。
- 若数据标签是可配置接口，写成“由数据标签规定”，并在指南书或配置文档中给出资源位置。
- 原版已经显示的攻击力、攻击速度、耐久和采掘属性不重复描述。
- 简化版使用定性表述；Shift 版在同一句中替换为精确数值。

## 8. 事实边界

撰写前将信息分为四级：

1. **确定事实**：代码行为、配置默认值、配方、模型与资源，可直接写。
2. **已确认设定**：用户明确给出的名称、元素联系与象征，可直接写。
3. **合理观察**：例如法环悬于背后、光禅杖自上而下坠落，可写成视觉描述。
4. **未知设定**：制造者、组织、年代、宗教和历史，一律不补写。

禁止使用“无名工匠”“失落文明”“古老教团”等套语掩盖设定缺失。

## 9. 不属于叙述文案的内容

以下内容以清晰和一致为优先，不套用物品叙事结构：

- 物品名、方块名和创造模式分页名；
- GUI、容器、按钮和 JEI 标签；
- 死亡消息与即时系统反馈；
- 坐标、机器数值和纯技术状态；
- Shift、Alt 与单位格式等 Tooltip 控制文本。

## 10. 审校清单

每条文案提交前检查：

- 去掉名称后，描述是否仍能指向这件物品？
- 默认版是否一句话说明核心身份与能力？
- Alt 是否真正替换简述，并补充机制细节？
- Shift 是否只把数值嵌入原句？
- 是否重复原版属性栏已有信息？
- 是否出现代码不能证明的人名、组织或历史？
- 是否混入实现术语、占位文本、翻译腔或无关笑话？
- 中英文是否表达同一事实，并保留相同占位符？
- JSON、Patchouli 标记和翻译参数是否通过自动校验？
